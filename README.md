## 3. Project Overview

The objective of this project is to develop a machine learning system that predicts ATM cash withdrawal demand in Dehradun.

The project follows an end-to-end MLOps workflow covering:

- Data investigation and quality assessment
- Data versioning using DVC
- Data loading, cleaning, and preprocessing
- Machine learning model development
- Experiment tracking and evaluation with MLflow
- **Stage 3: REST API development, containerisation, CI, and Kubernetes deployment**
- Model monitoring and retraining

## 4. Dataset Description

The project uses three datasets:

| Dataset | Description | Records |
|---|---|---:|
| `train.csv` | Historical training dataset | 1000 |
| `later.csv` | Later-period dataset for monitoring | 300 |
| `holdout_features.csv` | Holdout dataset for final predictions | 250 |

**Prediction target:** `withdrawal_thousand_rs`

The holdout dataset does not contain the target column.

### Original Dataset Columns

- `record_id`
- `date`
- `nearby_shops`
- `days_to_salary`
- `footfall_index`
- `distance_to_market_km`
- `avg_ticket_rs`
- `other_atms_1km`
- `atm_type`
- `area`
- `withdrawal_thousand_rs` (not available in holdout)

## 5. Data Investigation Findings

The initial investigation identified the following data-quality issues:

| Data issue | Finding | Action |
|---|---|---|
| Data leakage | No leakage identified | No action required |
| Unit inconsistency | Highway distances in training data recorded in metres | Converted to kilometres |
| Sentinel values | `avg_ticket_rs` contains -999 in 54 training records | Replaced with missing values |
| Duplicate rows | No duplicate rows | No rows removed |
| Stuck sensor | `days_to_salary` contains repeated values of 22 | Retained without modification |
| Target anomalies | No 10× target typo group identified | No correction required |
| Category inconsistencies | `atm_type` contains spelling and formatting variants | Normalized into three categories |

Detailed findings are documented in `reports/findings.yaml`.

## 13. API Endpoints

### GET `/health`

Liveness and readiness probe.

**Response:**

```json
{
  "status": "ok",
  "model_loaded": true,
  "model_path": "/absolute/path/to/models/model.joblib"
}
```

---

### POST `/predict`

Predict ATM cash withdrawal demand.

**Request body (JSON):**

| Field | Type | Constraints | Description |
|---|---|---|---|
| `nearby_shops` | float | — | Number of nearby shops |
| `days_to_salary` | float | — | Days until next salary day |
| `footfall_index` | float | — | Daily footfall index |
| `distance_to_market_km` | float | ≥ 0 | Distance to nearest market (km) |
| `avg_ticket_rs` | float | **≥ 250** | Average ticket size in Rs |
| `other_atms_1km` | float | 0 – **30** | Competing ATMs within 1 km |
| `atm_type` | string | `bank_branch` \| `mall` \| `standalone` | ATM type |
| `area` | string | `Highway` \| `Market` \| `Residential` | Area classification |

**Example request:**

```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "nearby_shops": 12,
    "days_to_salary": 7,
    "footfall_index": 55.0,
    "distance_to_market_km": 2.5,
    "avg_ticket_rs": 1500.0,
    "other_atms_1km": 3,
    "atm_type": "mall",
    "area": "Market"
  }'
```

**Example response:**

```json
{
  "predicted_withdrawal_thousand_rs": 182.47,
  "model": "atm_cash_demand_model@champion",
  "status": "success"
}
```

## 14. Input Validation Rules

| Rule | HTTP status |
|---|---|
| `other_atms_1km` > 30 | 422 |
| `avg_ticket_rs` < 250 | 422 |
| Invalid `atm_type` (not `bank_branch`, `mall`, or `standalone`) | 422 |
| Invalid `area` (not `Highway`, `Market`, or `Residential`) | 422 |
| Missing required field | 422 |
| Extra unexpected field | 422 |
| Malformed JSON | 422 |
| Model artifact missing | 503 |
| Inference error | 500 |

## 16. Structured JSON Logging

The API emits structured JSON logs to stdout. Each log entry includes:

| Field | Description |
|---|---|
| `timestamp` | ISO 8601 UTC timestamp |
| `level` | Log level (`INFO`, `WARNING`, `ERROR`) |
| `logger` | Logger name |
| `message` | Human-readable message |
| `endpoint` | API route (`/health` or `/predict`) |
| `error` | Error detail (error events only) |

Example log line:

```json
{"timestamp": "2026-11-26T07:30:00+00:00", "level": "INFO", "logger": "mp293.api", "message": "Prediction successful", "endpoint": "/predict", "predicted_withdrawal_thousand_rs": 182.47, "status": "success"}
```

No sensitive information or raw user input is logged.

## 18. GitHub Actions CI

The workflow is defined in `.github/workflows/ci.yaml`.

It runs on every push and pull request to `main` and:

1. Sets up Python 3.11
2. Installs all dependencies
3. Runs Stage 1 & 2 tests (`test_data_loader`, `test_preprocessing`, `test_train`)
4. Runs Stage 3 API unit tests (mock-based; no model artifact required)
5. Validates Kubernetes YAML with `yamllint`

> Tests that require `models/model.joblib` or the raw CSV files are skipped in CI.

## 20. Troubleshooting and Known Limitations

| Issue | Cause | Resolution |
|---|---|---|
| `503 Service Unavailable` on `/predict` | `models/model.joblib` missing | Run `python -m src.mp293.export_model` |
| `RuntimeError: Cannot load model` on startup | MLflow DB missing or no champion alias | Ensure `mlflow.db` is present and Stage 2 was run |
| DVC pull fails | No remote configured | Obtain raw CSVs from project owner |
| Docker build fails at `COPY models/model.joblib` | Artifact not exported yet | Export model first, then build |
| CI skips integration tests | `models/model.joblib` not in Git | Expected; model artifact is not committed to Git |
| Kubernetes deployment pending | Image not in cluster registry | Load image into cluster: `minikube image load mp293-api:1.0` |
